What this configuration is

The firm UI configuration is a single JSON object stored on the firm record (FirmConfiguration.uiConfig). It lets a firm switch front-end behaviour on and off — page titles, widget visibility, default date ranges — without a back-end change or a code deployment. The front-end team owns its shape; it is typed as IUiConfiguration.

How your JSON is applied

On load the app deep-merges your JSON over a complete set of defaults: merge({}, DEFAULT_UI_CONFIGURATION, uiConfig). Three consequences matter:

  • Omitting a key is safe. Anything you leave out keeps its default value, so a partial configuration is perfectly valid.
  • A key in the wrong place is silently ignored. The merge happily adds it to the merged object, but no component ever reads that path — so nothing happens and there is no error anywhere. This is the single most common support issue, and the main thing this page checks.
  • Arrays merge by index, not by replacement. See the warning below.
Arrays are merged element by element

merge combines arrays position by position. If the default navigationWidget.cards has 6 entries and you supply 2, you end up with 6 cards: yours in positions 1–2 and the untouched defaults in positions 3–6. To remove a card, supply the full array and set "visibility": false on the entries you do not want — do not shorten the array.

Never rely on a key being absent

Every boolean is explicit. Set true or false; absence means “use the default”, which is not the same as false. Names are always positive (showX, never hideX) except where noted.

What “Verify” checks

  • JSON syntax — with the line and column of the first parse failure.
  • Duplicate keys — legal JSON, but the last one silently wins.
  • Unknown fields — keys no component reads, with a close-match suggestion when it looks like a typo.
  • Misplaced fields — a real field sitting at the wrong path, reported with the exact path the app reads instead. Fix placement relocates the unambiguous ones for you.
  • Types and allowed values — booleans that arrived as "true" strings, enums outside the supported set, objects where an array belongs.
  • Field-specific rules — bilingual labels missing fr, more than six visible navigation cards, short cards arrays, unsupported icon keys, suspicious links.
  • Defaults in effect — every key you omitted and the value it falls back to (enable Notes in the result filters).
Annotation keys are recognised, not flagged

JSON has no comment syntax, so notes are conventionally written as keys: "Note", "Note2", "showApiTagVersion-WARNING", or any key ending in -WARNING, -NOTE, -TODO or -COMMENT, and any key starting with _. These are reported as notes rather than errors: the app ignores them, which is exactly what they are for. Keep them.

A finding that repeats across array entries — the same missing key in every navigation card, say — is collapsed into one row with a ×N count, while the annotated view still highlights every individual line.

Versions

The Version picker at the top of the page selects the release to validate against. It changes the allowed values, the defaults and this field reference, and it is remembered between visits. Pick the release the firm is actually running — a value that is fine on develop can be rejected on an older release.

The email assistant is the trap when downgrading

On 6.0 and 6.1, sending two tones does not give a firm two tones. Positions 1–2 are your entries merged key by key over the first two built-ins, and positions 3–4 are the remaining built-ins, untouched. The same configuration on 6.2 yields exactly the two tones you sent.
